Разработай конкретные входные потоки Xinertel для выбранного теста, учитывая общую
базу и дельту. Это действия и содержимое отправляемых кадров. Ожидаемые выходные
пакеты и отбрасывания будут описаны отдельно в критерии прохождения.

Формат результата — JSON по response_schema:
- flows: последовательно пронумерованные потоки. Для каждого укажи requirement_codes,
  port (номер Xinertel), dut_interface (точное имя из port_mapping), packet_count,
  fields (список полей кадра без нумерации) и load (нагрузка и длительность).
- parameters: новые параметры трафика, ключи без ${}. Для каждого верни объект
  с value (значение строкой или null, если неизвестно) и note (краткое примечание).
  Например: "TTL_INIT": {"value": "64", "note": ""}.
  В value помещай только значение с единицами при необходимости, без объяснений.
  Неизвестные IP/MAC не выдумывай: value = null, в note укажи, чей это адрес.
  Параметры конфигурации не переопределяй.
- notes: дополнительные существенные факты, если они нужны. По умолчанию пустой список.
  Программа сначала перечислит все переменные со значениями, а затем отдельно
  соберёт note и notes в примечания раздела «Дополнительная информация».
  Не повторяй значения и содержание потоков. Если значение самоочевидно, note оставь пустым.
  Примечание — короткое условие или факт, а не объяснение рассуждений модели.
- unresolved_requirements: code и reason для АТ, воздействие для которых нельзя
  полностью обосновать. Это явный пробел сценария, а не успешно покрытое требование.
  Если для части составного АТ есть потоки, а для части нет, укажи его и здесь.
  reason — краткое недостающее условие, без рассуждения о всём сценарии.

В итоговом README программа добавит общие шаги:
1. Применить конфигурацию DUT (см. раздел «Конфигурация устройства»).
2. Запустить захват трафика на всех портах Xinertel текущей топологии.
3. Последовательно запустить сформированные потоки.
Затем оформит каждый поток в человеческом формате, например:

<ТР GRE-VERSION-NUMBER.1, GRE-RESERVED0-BITS.1, GRE-PROTOCOL-TYPE.1:
Поток 1
1 кадр на port_3 (DUT xe-0/0/2) со следующим содержанием:
1. Формат Ethernet II;
2. SRC MAC = ${MAC_A};
3. DST MAC = ${MAC_DUT_P3};
4. EtherType = 0x0800 (IPv4);
5. SRC IP = ${P5_2}; DST IP = ${G1_2};
6. TTL = ${TTL_INIT};
7. Размер кадра (без FCS) = ${FRAME_SIZE} байт;
8. Нагрузка: 1 кадр за ${FLOW_DURATION} секунд.
ТР>

Пример показывает оформление, а не назначает порты и адреса текущего теста.
Не копируй port_3, MAC_A, P5_2 и другие имена, если для текущей конфигурации
нужны иные значения. Общие шаги и маркеры ТР в JSON возвращать не нужно.

Правила сценария:
- Пиши кратко, как спецификацию кадра: поле и значение. Не включай в fields/load
  объяснения маршрутизации и повтор назначения потока. Связи параметров указывай
  только в note параметра, однократно и кратко. Не расписывай произвольные UDP-порты,
  IHL и арифметику размеров, если они несущественны для выбранных АТ.
  Не добавляй лишних условий вроде «TTL не равен 255», если это не следует из АТ.
  Все поля каждого потока в JSON задавай полностью; повторяющиеся поля программа
  сократит в README до отличий от полностью описанного потока. Сохраняй одинаковые
  названия и группировку полей у похожих пакетов, не меняя содержание.
- Каждый выбранный АТ должен быть связан с потоками или явно отмечен как
  неразработанный. Один поток может относиться к нескольким АТ, один АТ —
  к нескольким потокам. Не объединяй разные значения поля в расплывчатое «варьировать»:
  задай отдельные потоки для нужных вариантов пакета.
- Для составных АТ с формированием и приёмом предусмотрите оба направления.
  Проверка формирования GRE требует входного обычного IPv4, направленного маршрутом
  в туннель; проверка приёма GRE требует входного GRE-пакета на underlay-порту.
- Порты и интерфейсы бери только из port_mapping. Этот порядок — предлагаемая
  коммутация стенда, а не подтверждённое физическое подключение.
- Адреса и MAC из конфигурации переиспользуй с теми же именами. Новые неизвестные
  значения обозначай ${PARAMETER}; не подставляй вымышленные конкретные IP/MAC.
  Для каждого нового параметра укажи смысл и связи с адресацией конфигурации.
  Например, адрес назначения для инкапсуляции должен попадать в сеть маршрута через GRE.
- fields должны однозначно задавать Ethernet II, SRC/DST MAC, EtherType и IPv4
  SRC/DST, TTL, размер кадра без FCS. Для входного GRE разделяй внешние IPv4/GRE
  заголовки и внутренний IPv4; задавай необходимые Protocol, Version, Reserved,
  Protocol Type, Checksum Present и Checksum/Reserved1 при их наличии.
  Для checksum указывай способ вычисления или именованный параметр с точным определением.
  При C=0 поля Checksum и Reserved1 отсутствуют; при C=1 оба присутствуют.
  Явно задавай Checksum Present (C), Checksum и Reserved1 в соответствующих потоках;
  не смешивай optional-поля с битами Reserved0 и не добавляй поля RFC 1701 без необходимости.
- Не меняй проверяемое поведение DUT настройками, которых нет в конфигурации.
  Не объявляй назначенный EtherType неподдерживаемым DUT без подтверждения;
  неизвестную поддержку нельзя подменять произвольно выбранным отрицательным сценарием.
  Отправка пакета с Reserved1 в DUT не проверяет формирование Reserved1 самим DUT.
  Если не подтверждено, как заставить DUT сформировать требуемое поле, укажи это
  в unresolved_requirements; не придумывай настройку или результат.
  В текущем профиле Junos нет подтверждённой настройки формирования исходящего
  Checksum/Reserved1: АТ формирования Reserved1 требует явного уточнения этого условия.
- Для предотвращения петли задай конкретный выбор параметра внутреннего DST IP
  и обоснуй связь с конечными точками и объявленными маршрутами. Если условия
  возникновения проверяемой петли не установлены, явно укажи недостающее условие.
- load должен описывать объём и длительность передачи; по умолчанию достаточно
  одного кадра на вариант. Не придумывай требования к производительности и pcap-файлы.
- Не добавляй настройки DUT, действия commit/NETCONF, критерии успешности, заголовки
  README и списки проверок валидатора. Все строки fields и load — однострочные.
