# Генератор описаний тестов

Прототип для дипломной работы: **требования → описание теста**.

Сейчас LLM разбивает весь файл атомарных требований на тесты, затем формирует
код и краткое описание каждого теста. Теги и трассировка требований
собираются из входного JSON без LLM. Топология, конфигурация, воздействие,
критерий прохождения и дополнительная информация пока содержат `TODO`.

## Установка

Нужен Python 3.11 или новее. Из корня проекта:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install "openai>=1.0.0" "pydantic>=2.0.0" "python-dotenv>=1.0.0" "doit>=0.36.0"
cp .env.example .env
export PYTHONDONTWRITEBYTECODE=1
```

Устанавливаются только зависимости; устанавливать сам проект не нужно.
Локально команда `doit` также настроена в `~/.zshrc`: использует `.venv`
текущего проекта и отключает кеш Python без активации окружения.

## Запуск

```bash
doit          # Разбиение всего файла и генерация описаний через LLM
doit draft    # Проверка без LLM: одно АТ на тест, названия — заглушки
doit list     # Список задач
doit clean    # Удалить весь каталог outputs
```

Файл требований задаётся в начале `dodo.py`: `REQUIREMENTS`.
Ручного выбора АТ больше нет — обрабатывается весь файл.
Текущий вход — `requirements/GRE_RFC2784.json`; этот каталог не хранится в Git,
поэтому после клонирования входные данные нужно добавить отдельно.

После успешного прогона следующая генерация выполняется заново. Результаты сохраняются в
`outputs/requirements_to_description/generated/`, а запуск без LLM — в `draft/`.
Внутри каждого каталога находятся:

- `groups.json`: коды тестов, краткие описания, выбранные АТ, имена файлов и покрытие;
- `test_001.md`, `test_002.md`, …: отдельные описания всех тестов.

Разбиение сохраняется сразу, каждое описание — по мере готовности.
В `groups.json` поле `status` равно `in_progress` до завершения и `complete`
после успеха; покрытие относится к запланированным группам, а наличие `code`
и `short_description` у теста означает, что его описание уже сохранено.
После сбоя повторите `doit generate`: при неизменных требованиях, документе
формата, промптах и настройках модели будут использованы сохранённые этапы.
Чтобы начать заново, выполните `doit clean`, затем `doit generate`.

Разбиение и описания формируются разными LLM-запросами: сначала план всех тестов,
затем описание каждой проверенной группы. Итого один запрос на разбиение плюс
один запрос на каждый тест. Если разбиение не проходит проверку, описания не генерируются.
Ошибки соединения, HTTP 408/409/429 и 5xx повторяются до трёх раз с паузами
5, 10 и 20 секунд. Если сервис остаётся недоступен, прогон останавливается
с сохранением результатов; бесконечного повторения запросов нет.
`doit draft` проверяет сборку без API; его разбиение «одно АТ на тест» — техническая
заглушка, а не результат смысловой группировки. Метод записывается в `groups.json`.
При успешном повторном запуске файлы `test_*.md` заменяются новым набором.
`doit clean` удаляет весь каталог `outputs`, используя
служебную цель `erase`. Файл состояния doit находится в `.venv`.

## LLM и документ формата

В `.env.example` настроен бесплатный [Vireonix](https://vireonix.ai/docs)
без ключа: `LLM_BASE_URL=https://vireonix.ai/v1`, `LLM_MODEL=auto`.
`auto` не фиксирует модель, поэтому используется для отладки.
Для перехода на DeepSeek замените URL, ключ и модель в `.env`.
Без ключа заголовок авторизации не отправляется.

При каждом запросе LLM получает `docs/test_description_format.md` как инструкцию,
а выбранные атомарные требования — отдельно как данные. Примеры из инструкции
не являются данными текущего теста. При расхождении правил и примеров приоритет
у правил (например, `# Код`, а не `# Название`).

Markdown извлечён из `docs/Test-description-format-28-11-25-1.docx`.
DOCX не хранится в Git и не читается при запуске. При изменении исходника
нужно обновить Markdown-копию.

## Код

```text
main.py                              # Запуск из исходников
dodo.py                              # Задачи doit и входной файл
src/test_descriptions/
├── __main__.py                       # CLI и сохранение результата
├── rendering.py                      # Сборка Markdown
└── requirements_to_description/
    ├── pipeline.py                   # Последовательность шагов
    ├── requirements.py               # Модель, загрузка и выбор требований
    ├── grouping.py                   # Разбиение на тесты и проверка покрытия
    └── generation.py                 # Промпт, вызов LLM и проверка ответа
```

## Ограничения

Проверяются уникальность кодов входного JSON и тестов, непустые группы,
корректность кодов АТ и наличие родителей выбранных требований.
Одно АТ может входить максимум в один тест. Все MUST должны быть покрыты;
непокрытые необязательные АТ перечисляются в `groups.json`.
Рабочее правило распознавания АТ: `origin == "OTHER"` и непустой
`parentRequirementCodes`. Его нужно сверять при подключении новых наборов.

Ответ LLM проверяется как JSON с двумя непустыми однострочными полями:
`code` (до 60 символов) и `short_description`. Проверка покрытия опирается на
заявленные коды АТ и не доказывает, что текст теста действительно их проверяет.
Смысловая корректность группировки и описаний пока оценивается вручную.
