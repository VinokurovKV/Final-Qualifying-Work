# Генератор описаний тестов

Прототип для дипломной работы: **требования + RFC → общая базовая XML → группы тестов →
описания и топология → Delta XML → проверка и JSON → конфигурация и тестовое воздействие в README**.

## Входные данные

- `requirements/*.json` — требования.
- `docs/RFC*.pdf` — стандарты: PDF определяется по номеру RFC в имени JSON.
- `configurations/*.xml` — необязательные готовые базы для запуска с `--base`.
- `docs/test_description_format.md` — локальный документ формата README.

Готовая база не требуется: LLM генерирует общую XML-конфигурацию по требованиям,
тексту RFC, топологии и документированному контексту Junos XML/EX4650. Она используется
для дельт всех тестов текущего прогона. Идентификатор генерируемой базы — `BASE_RFC<номер>`.
При явном `--base` используется готовый файл, его идентификатор — имя без расширения.

## Установка

Нужен Python 3.11 или новее:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install "openai>=1.0.0" "pydantic>=2.0.0" "python-dotenv>=1.0.0" "doit>=0.36.0" "questionary>=2.0.0" "rich>=13.0.0" "pypdf>=5.0.0"
cp .env.example .env
export PYTHONDONTWRITEBYTECODE=1
```

Сам проект устанавливать не нужно. Локально `doit` настроен в `~/.zshrc`
и использует `.venv` текущего проекта. URL, ключ и модель задаются в `.env`.
Для DeepSeek создайте ключ в [личном кабинете](https://platform.deepseek.com/api_keys)
и укажите:

```env
LLM_BASE_URL=https://api.deepseek.com
LLM_API_KEY=<ваш ключ>
LLM_MODEL=deepseek-flash
```

DeepSeek использует OpenAI-совместимый API, отдельный SDK не нужен.
У API отдельный токенный биллинг: [тарифы](https://api-docs.deepseek.com/quick_start/pricing).
Для OpenRouter остаются `https://openrouter.ai/api/v1`, `openrouter/free` и ключ OpenRouter.
Ключи разных провайдеров не взаимозаменяемы. `.env` не хранится в Git.

## Запуск

```bash
doit          # Меню: требования → действие; выбора базы нет
doit generate # Полный цикл для REQUIREMENTS из dodo.py, включая генерацию базы
doit draft    # Черновики без LLM; разбиение по одному АТ — техническая заглушка
doit list
doit clean    # Удалить results
```

Явные входные данные:

```bash
.venv/bin/python -B main.py requirements/GRE_RFC2784.json
# Если PDF нельзя определить автоматически:
.venv/bin/python -B main.py requirements/GRE_RFC2784.json --rfc docs/RFC2784.pdf
```

Каждый запуск создаёт отдельный каталог `results/requirements_to_description/<имя JSON>/descriptions/run_YYYY:MM:DDTHH:MM:SS/`
с датой и временем по Москве, например `run_2026:11:20T15:30:45`.
При совпадении времени до секунды добавляется номер `_2`, `_3`, …; случайного суффикса нет.
Параметр `--output` задаёт родительский каталог. Старые прогоны не перезаписываются.
После сбоя выберите продолжение в меню или добавьте `--resume`: сохранённые этапы
используются только при совпадении требований, RFC (или явно заданной базы), промптов, кода и модели.
Сохранённая и проверенная общая база при продолжении повторно не генерируется.
Черновики `--no-llm` не требуют ни RFC, ни базовой XML и пропускают конфигурацию.

При необходимости можно сгенерировать только базу, без остальных разделов:

```bash
PYTHONPATH=src .venv/bin/python -B -m test_descriptions.requirements_to_description.base_configuration requirements/GRE_RFC2784.json --rfc docs/RFC2784.pdf
```

Отдельные прогоны базы сохраняются в `results/requirements_to_description/<имя JSON>/base_configuration/run_…/`.
В полном цикле база сохраняется в `configurations/BASE_RFC<номер>.xml`, её разбор —
в `json/base_configuration.json`, а запросы и ответы — в `diagnostics/base_generation.json`
внутри каталога прогона. Промпты базы — `prompts/rfc_base_*.md`; при ошибке
локального профиля допускается одна попытка исправления. Входные XML в `configurations/` проекта не заменяются.

Итоговый файл базы имеет формат системы: `edit-config` с `candidate`, `merge` и
`config/configuration`, затем `get-configuration`, `validate` и `commit confirmed`.
LLM генерирует блок `configuration`, Python проверяет его и добавляет обёртку из
`prompts/base_configuration_rpc.xml`. Это последовательность RPC в файле;
сама программа ничего не отправляет на устройство и не выполняет эти операции.
Текстовый промпт `device_configuration.md` отвечает только за описание настроек.

## Генерация и результат

Сначала генерируется и локально проверяется общая база RFC. Затем группировка получает
отдельные списки АТ и родительского контекста. Проверяются
коды, отсутствие повторов и покрытие MUST; смысловое качество групп оценивается отдельно.
Затем формируются код, краткое описание и топология каждого теста.
Теги и трассировка требований собираются из JSON.

Для конфигурации каждого теста LLM получает выбранные АТ, топологию и общую базу и возвращает
только Delta XML. Python проверяет XML и необходимые условия IPv4 GRE по базе и дельте:
unit, endpoints, family inet и путь инкапсуляции, когда его требуют АТ.
При ошибке выполняется одна попытка исправления. После успешной проверки отдельный
запрос формирует текст раздела конфигурации только по настройкам из JSON дельты,
без служебных флагов и ограничений проверки в контексте этого запроса.
Пустая дельта допустима, если подготовка уже есть в базе. Для неё программа
подставляет одну фразу об отсутствии изменений без дополнительного запроса LLM.

После конфигурации отдельный запрос генерирует тестовое воздействие: входные потоки
Xinertel с кодами АТ, портами и полями кадров. Модель получает выбранные АТ,
топологию, базу и дельту; сопоставление `port_N` с интерфейсами DUT задаёт программа
по порядку физических интерфейсов базы. Это предлагаемая коммутация стенда.
README содержит общие шаги применения конфигурации и захвата трафика, затем блоки
`<ТР … ТР>` с потоками. Неизвестные адреса и значения остаются параметрами;
новые параметры трафика поясняются в «Дополнительной информации».
В начале этого раздела перечисляются переменные со значениями, затем — короткие
примечания и дополнительные факты. Неизвестные значения отмечаются как «не задано»;
пояснения не включаются в строки значений.
Похожий поток описывается отличиями от полностью заданного потока: изменённые,
добавленные и исключённые поля перечисляются явно. В JSON все потоки остаются полными.

Проверяются номера потоков, ссылки на выбранные АТ, соответствие портов и объявления
параметров, а также явные противоречия C/Checksum/Reserved1. Для формирования
исходящего Reserved1 текущий профиль требует явного указания неподтверждённой подготовки DUT.
При ошибке формата или этих проверок допускается одна попытка исправления;
оба ответа и ошибка сохраняются в том же журнале. Это не полная проверка полей пакета.
Если воздействие для АТ нельзя обосновать, модель должна явно указать
неразработанную часть: она попадает в README и отчёт со статусом `needs_review`.
Наличие ссылки на АТ не доказывает его смысловое покрытие потоком.
Воздействие сохраняется в `json/groups.json`, а запрос и ответ — в
`diagnostics/test_001.stimulus.json`. После сбоя сохранённые этапы повторно не генерируются.

На верхнем уровне прогона находятся только основные результаты — описания тестов:

```text
run_2026:11:20T15:30:45/
├── test_001.md
├── test_002.md
├── configurations/
│   ├── BASE_RFC2784.xml
│   ├── test_001.delta.xml
│   └── test_002.delta.xml
├── json/
│   ├── groups.json
│   ├── requirements.json
│   ├── base_configuration.json
│   ├── test_001.configuration.json
│   └── test_002.configuration.json
└── diagnostics/
    ├── base_generation.json
    ├── grouping.json
    └── validation_report.md
```

`json/groups.json` содержит группы, трассировку и прогресс для продолжения.
Журналы `diagnostics/base_generation.json` и `diagnostics/grouping.json` объединяют
входные данные, промпты, ответы и метаданные запросов. Отклонённые версии базы
сохраняются в журнале; первоначальные ошибочные дельты — в `diagnostics/test_001.delta.initial.xml`.
При запуске с готовой базой или без LLM ненужные артефакты не создаются.

В разделе конфигурации README остаются идентификатор базы и описание изменений.
Служебные ограничения и признаки шаблона сохраняются в JSON и отчёте, включая
ошибки отклонённых дельт и ожидание текста при сбое запроса LLM.

Все промпты вынесены в `src/test_descriptions/requirements_to_description/prompts/`.
Критерий прохождения пока содержит TODO. В дополнительной информации появляются
определения параметров трафика; конкретные адреса стенда пока не назначаются.
В черновиках без LLM тестовое воздействие также остаётся TODO.

## Пределы проверки

Адресные связи проверяются по объявленной базе и дельте: source GRE должен быть
локальным адресом физического интерфейса, ARP-соседи и IP next-hop — разрешаться
через подходящие подключённые подсети. Для endpoint проверяется путь через underlay,
включая конкретные статические маршруты, более специфичные discard/reject и путь через GRE.
Рекурсивное разрешение статических next-hop этим профилем не подтверждается.
Для неизвестных адресов результат — `pending_address_bindings`, а не подтверждённая
достижимость. Условия подстановки параметров сохраняются в JSON и `diagnostics/validation_report.md`.
Количество физических соединений в топологии согласуется с общей базой прогона.

Локальный профиль не заменяет Junos XSD, NETCONF validation или проверку на устройстве.
Объединение известных настроек базы и дельты учитывает merge/replace/delete/remove,
но не вычисляет реальное состояние DUT. Направление проверки определяется по тексту АТ;
связи параметров, конкретный трафик и достаточность сценария требуют отдельной оценки.
Программа не применяет конфигурацию и не выполняет commit.

Входные XML могут содержать именованные параметры неизвестных адресов.
Эталонные группы не подставляются вместо ответа LLM.

`requirements/`, `configurations/`, `docs/`, `.env`, `results/` и `experiments/` исключены из Git.
Локальные входные документы после клонирования нужно добавить отдельно.
Локальные входные данные и `experiments/` сохраняются после `doit clean`.
